# ARCHITECTURE.md

## What we're building and why

Hindsight is a debugger built around the assumption that an AI is the primary reader of debug output. It records the complete execution of a program — every function call, every variable assignment, every branch taken — into a structured trace, then exposes that trace to language models via the Model Context Protocol so they can answer questions about what the program actually did.

The motivation is simple. Debugging today is dominated by the cost of human attention. When a program misbehaves, an engineer reproduces the bug, sets breakpoints, steps through execution, inspects variables, forms a hypothesis, tests it, and iterates. Most of that work is mechanical correlation: looking up where a value came from, walking back through the code paths that produced it, comparing what happened to what should have happened. The actual diagnosis — "ah, this variable is null because that earlier check returned the wrong type" — is fast once you have the relevant evidence in front of you. The slow part is finding the evidence.

The category of debugger that records full execution history and lets you query it after the fact is called omniscient debugging. It's been around since 2003. It never became standard practice because the trace data, while complete, was too large for humans to navigate efficiently. You could capture everything, but you still had to know what to look for, where to look, and how to interpret what you found. The tool produced a haystack and asked you to find a needle.

That cost structure inverts when the reader of the trace is a language model. An AI can ingest a structured trace, perform causal slicing automatically, correlate variable changes with branch decisions, and produce a narrative explanation in seconds. The omniscient debugging idea was right; it was waiting for the right consumer. Hindsight is the version of that idea built for an AI consumer from the ground up.

The design has three components in series. A recorder runs alongside a program being debugged and emits a stream of events to a binary trace file. An indexer ingests that trace file into an embedded analytical database that supports efficient queries over the event stream. A Model Context Protocol server exposes a small set of debugging primitives — get a variable's value at a point in time, find the chain of assignments that produced it, list calls to a function, retrieve relevant source code — to any MCP-compatible client. The user interacts with their preferred AI client (Claude Code, Claude Desktop, a local model wrapped in an MCP shim) and asks questions in natural language. The AI calls the MCP tools, queries the trace, and explains what happened.

The reason for separating these components rather than building one monolithic tool is that each layer has a different rate of change and a different audience. The trace format will evolve slowly because every recorder and every analyzer depends on it; we want it to be stable. The indexer benefits from improvements in DuckDB and Arrow that we get for free by depending on them. The MCP server's tool surface evolves as we learn what AI consumers need. The recorder is the most language-specific component; we want it to be small and replaceable so that adding a new language (Python now, then C++, then Rust, then whatever the community wants) doesn't require touching the rest of the system. The clean separation also means the trace format becomes a protocol that other projects can implement against, rather than an internal detail of our tool.

## The trace format

The trace format is the contract between recorders and everything else. It's a binary file with a header, a sequence of events, and periodic checkpoints that allow seeking into the middle of a trace without reading from the start. Events are length-prefixed and self-describing enough that a reader can skip over events it doesn't understand, which gives us forward compatibility when we add event types in later versions.

We use a custom format rather than an existing one because the existing options don't fit cleanly. Apache Parquet is excellent for analytical columnar data that's written in batches and queried later, but a debug trace is appended event-by-event in real time, with mixed event types that don't naturally fit a fixed columnar schema. Protocol Buffers handle the schema well but their wire format isn't designed for streaming append with low overhead. We get more flexibility and better performance by defining our own format and optimizing it for our specific access patterns: streaming append on the writer side, fast scan and seek on the reader side.

The format is documented in detail in `docs/trace-format.md`, which is the source of truth. The implementation lives in the `hindsight-format` crate and provides both writer and reader APIs. Writers are typically constructed once per recording session and consume events sequentially. Readers can either iterate the trace from the start or seek to a checkpoint and iterate from there. The format library has no knowledge of how events are produced or how they'll be queried — it only handles encoding and decoding bytes.

Values inside events — the actual program data, like the contents of a variable at the moment it was assigned — are the trickiest part of the format. We can't capture every value verbatim because the size of even a small program's full state across an entire execution is enormous. We also can't capture too little because losing a value means losing a query path. The compromise is a tiered representation. Primitive values (integers, floats, booleans, short strings, null) are stored inline in their native form. Larger or more complex values are stored as a structured summary: their type, a deterministic hash of their content, a length where applicable, and a truncated text representation. The hash lets the AI ask "is this the same value as that earlier one" with certainty even when both are too large to compare in full. The truncated representation is what the AI actually reads when it wants to know what was in the value. This compromise works because debugging questions are rarely about the full content of a 10-megabyte tensor; they're about whether two values match, what shape something has, whether it has the expected type, and what the first few elements look like.

The user can register custom capture handlers for their own types if they need richer representations. Beyond manual handlers, we also expose MCP tools that let the AI itself define new capture behaviors during a debugging session. If during analysis the AI determines that a particular property would be valuable to capture on future runs — for instance, the user is debugging a sparse matrix problem and the AI realizes that the locations of zero entries are what matter, not the dense values — it can register a custom capture handler through the MCP interface. The next recording session then automatically captures that property whenever the relevant type is encountered. This makes capture itself adaptive: the system learns from each debugging session what's worth recording, and the AI's understanding of the problem domain feeds back into what the recorder collects. Custom handlers registered this way are stored alongside the trace metadata so they persist across sessions and can be shared with other users debugging similar problems.

## The indexer

A raw trace file is a sequential log of events. To answer questions like "what was the value of `x` at line 47 inside `process_request`," we need to be able to jump directly to that event without scanning from the beginning. To answer questions like "show me every assignment to `x` across the entire trace," we need a columnar layout that can scan one field across all events efficiently. This is what the indexer provides.

The indexer reads a `.hindsight` trace file and writes its contents into an embedded DuckDB database. DuckDB is an analytical database that runs in-process — no server, no setup, just a library you link against and a single file on disk that holds the database. It speaks SQL, supports the queries we need, and is fast enough that even traces with billions of events can be queried in milliseconds for typical questions. We use it because it solves a problem we'd otherwise have to solve ourselves and because choosing it makes the project smaller without making it less capable.

The schema is straightforward. There's an events table keyed by a monotonically increasing event ID and indexed by timestamp, function, and source location. There's a values table keyed by a content hash, with each unique value stored once regardless of how many times it appears in the trace — this deduplication is significant in practice, because most variables hold the same value across many events. There's a functions table that maps function IDs to names and source locations. There's a source files table that holds the actual source code of the program being debugged, hashed by content, so the AI can request source for any location referenced in the trace.

We use Apache Arrow as the in-memory representation of trace data when moving it from the format reader into DuckDB. Arrow is a standard columnar memory format that DuckDB consumes natively, which means we don't pay a serialization cost to load events into the database. Arrow is also the lingua franca of the modern data tooling ecosystem, so users who want to do ad-hoc analysis of their own traces with Python tools (pandas, Polars, NumPy) can do so without us writing any extra integration. The trace format on disk is our own; the in-memory representation while indexing is Arrow; the database is DuckDB. Each format does what it's best at.

The indexer lives in the `hindsight-index` crate. It exposes a single function that takes a path to a trace file and a path where the indexed database should be written, and produces the indexed file. Indexing is one-directional — once a trace is indexed, the original `.hindsight` file isn't strictly needed anymore for queries, though we keep it around for re-indexing if the indexer schema changes in a future version. Indexing a trace happens once, before the user starts a debugging session; queries run against the indexed form afterward.

## The MCP server

The MCP server is what makes Hindsight an AI tool rather than just a database with a fancy capture mechanism. Model Context Protocol is an open standard published by Anthropic that defines how AI clients can call tools provided by external servers. The protocol handles the wire format, authentication, schema declaration, and lifecycle. A Hindsight MCP server is a process that, when launched, advertises a set of tools to whatever AI client connects to it, then handles tool calls by querying the indexed trace and returning structured responses.

The set of tools we expose is intentionally small. There's a tool to get the value of a named variable at a point in time. A tool to get the history of a variable's values across some time range. A tool that performs causal slicing — given a variable and a time, walk backward through the data dependencies that produced its value and return the chain of assignments and branches involved. A tool to find function calls matching some predicate. A tool to retrieve the call stack at a point in time. A tool to fetch source code for a given file and line range. A tool to list exceptions raised during the trace. A tool to compute the diff between program states at two times.

The smallness is deliberate. AI tool design works best when each tool does one thing clearly, the AI composes them to handle complex requests, and the schemas are unambiguous. Adding more tools is tempting because each one looks helpful in isolation, but every additional tool dilutes the AI's ability to choose the right one and increases the prompt budget consumed by tool definitions. We start small, watch how AI clients actually use the tools we have, and add new ones only when there's a clear pattern that the existing tools can't compose to handle.

The MCP server is stateless across sessions. It opens the indexed database in read-only mode, handles tool calls by issuing SQL queries, and returns results. It doesn't maintain any cross-call state, doesn't cache results between requests, and doesn't write to the database. This makes it trivially safe to run multiple debugging sessions concurrently against the same trace, and it makes the server easy to reason about: every tool call is a pure function of the database contents.

The server lives in the `hindsight-mcp` crate. It uses the official Rust MCP SDK from Anthropic to handle the protocol layer. We supply the tool implementations and the database connection; the SDK handles message framing, lifecycle, and the rest of the protocol. Running the server is just a matter of pointing it at an indexed database and starting it.

## The Python recorder

The recorder is the language-specific component, and Python is our first target. It uses the `sys.monitoring` API introduced in Python 3.12 (PEP 669), which provides low-overhead hooks for the events we care about: function calls, function returns, line execution, exceptions, and branch decisions. We register handlers for these events and, when they fire, capture the relevant state and emit it through the trace format library to a `.hindsight` file.

The recorder is written in Python because `sys.monitoring` is a Python API, but the actual encoding of events into the trace format happens in Rust via PyO3 bindings. The Python side is thin: it hooks the interpreter, captures `frame.f_locals` for variable state, and hands events to the Rust side as fast as possible. The Rust side handles serialization, value summarization, and writing to disk. This split keeps the Python overhead minimal — the Python recorder is essentially a few hundred lines of glue — and concentrates the performance-sensitive work in the Rust core where it can be optimized once and benefit every language that uses the format.

Scope control is the most important design decision in the recorder. Recording every line of every function in a real Python program produces traces that are too large and too slow to be useful. The default is to record nothing, and the user opts in to recording specific functions via a decorator (`@hindsight.record`) or a context manager. Inside a recorded scope, all called functions are also recorded by default, but the user can exclude specific patterns from a config file. This gives the user precise control over the cost-coverage tradeoff: record everything in the small region where you're hunting for the bug, exclude the well-trusted math kernel that doesn't need recording, accept the resulting slowdown only where it buys you debugging value.

Value capture follows the tiered representation described in the trace format section. Primitives are captured directly. Containers (lists, dicts, tuples) are captured to a configurable depth and length, with elements beyond the limit summarized. Custom objects are captured as their type, their `id()`, a hash of their `repr()`, and the first portion of `repr()`. NumPy arrays and other large numeric types get special handling: shape, dtype, hash, and a small sample of values rather than the full contents. The user can register custom capture handlers for their own types if they need richer representations.

The recorder is in `crates/hindsight-py` (the Rust side, exposed via PyO3) and `recorders/python` (the Python package built with maturin). Users install it as `pip install hindsight-debug` (or whatever name we end up with on PyPI) and import it as `import hindsight`.

## The CLI

The CLI is a thin Rust binary that orchestrates the other components. It exposes three primary subcommands. `hindsight record <command>` runs an arbitrary command with the recorder enabled and writes a trace file. For Python, this means launching Python with the recorder pre-imported and configured. `hindsight index <trace>` produces an indexed database from a trace file. `hindsight serve <indexed_trace>` starts the MCP server pointed at an indexed trace, ready for an AI client to connect.

There's also a convenience subcommand `hindsight debug <trace>` that combines indexing (if not already done) and serving in one step, since that's the most common flow. The CLI prints clear instructions on first use about how to connect Claude Code or another MCP client to the running server.

The CLI lives in `crates/hindsight-cli`. It uses `clap` for argument parsing and depends on the other Hindsight crates. It contains very little logic of its own; it's a coordinator.

## How it all fits together

A typical user session looks like this. The user has a Python script with a bug they don't understand. They add a `@hindsight.record` decorator to the function where the bug is. They run `hindsight record python their_script.py`, which produces `trace.hindsight`. They run `hindsight debug trace.hindsight`, which indexes the trace into `trace.hindsight.db` and starts an MCP server. They've already configured Claude Code to know about the Hindsight MCP server. They open Claude Code and say "this trace has a bug where the function returns None instead of the expected dict, can you figure out why." Claude Code calls the MCP tools, which query the indexed database, which returns structured results. Claude composes the results into an explanation: "the function entered with valid input, processed three of the four expected branches, but at line 84 the conditional `if user.has_permission()` evaluated to False because `user.permissions` was an empty set rather than the expected set containing `read`. This empty set was set at line 22 of `auth.py` where the cache lookup returned the default empty value because the cache key was malformed."

The user reads this and either fixes the bug or asks follow-up questions. The follow-up questions also resolve to MCP tool calls. The whole session might involve dozens of tool calls but the user only sees the natural-language conversation.

## Performance targets

Recording overhead, measured as wall-clock slowdown of the program being recorded relative to running without the recorder, should be under 10x for typical programs in v0 and improve in later versions. This is a soft target; some programs will be slower, particularly those that do many small function calls or assign variables in tight inner loops. The user can scope the recorder to avoid hot regions where this is a problem.

Indexing throughput should exceed one million events per second on commodity hardware. A trace with ten million events should index in under fifteen seconds.

Query latency, measured from MCP tool call to response, should be under 200 milliseconds for typical queries on traces of up to one billion events. This is feasible because DuckDB's analytical performance is well-suited to our query patterns and because we deduplicate values aggressively, keeping the actual database size much smaller than the raw event count would suggest.

These targets are guides, not gates. We ship v0 when the system works on representative demos, even if performance is below target on edge cases. Performance is iterated after correctness.

## What v0 includes and excludes

V0 includes the Python recorder for Python 3.12 and later, the trace format with the events listed above, the indexer producing a DuckDB file, the MCP server with the tool surface listed above, and the CLI. It targets Linux, macOS, and Windows on x86_64 and arm64. It produces functioning end-to-end debugging on programs of moderate size — say, a few thousand lines of Python with traces in the megabyte to gigabyte range.

V0 excludes everything else. No C++ recorder, no Rust recorder, no support for Python 3.11 or earlier. No distributed tracing, no networking, no multi-process traces. No web UI. No live debugging or step-through (this is offline analysis only). No replay or re-execution from traces. No authentication, no multi-tenancy, no cloud sync. No support for capturing GPU state, network traffic, database queries, or anything beyond Python program state. These are all reasonable later additions, and the architecture supports them, but they aren't in v0 and shouldn't sneak in.

## Why these choices and not others

There are a number of decisions in this design that have plausible alternatives, and it's worth being explicit about why we chose what we chose so that future contributors don't reopen them casually.

We chose Rust for the core because the project will outlive any individual language fashion, the performance properties of Rust suit the workload, the ecosystem for the libraries we need (Arrow, DuckDB, MCP, PyO3) is excellent, and the borrow checker provides correctness guarantees that benefit a project being written largely with AI assistance. We considered C++ and rejected it because the build system pain (CMake, dependencies, cross-platform) is real and Cargo is decisively better. We considered Go and rejected it because Go's FFI story is weaker and we need clean integration with Python and eventually with C and C++ recorders. We considered Zig and rejected it because the ecosystem is too young for our dependencies.

We chose DuckDB because it solves the embedded analytical database problem definitively and is actively developed. We considered SQLite and rejected it because row-oriented storage hurts our analytical query patterns. We considered ClickHouse and Postgres and rejected them because they require running a server, which we explicitly don't want.

We chose Apache Arrow as the in-memory representation because it's the standard, DuckDB consumes it natively, and it gives us free interop with Python data tooling. The alternative was rolling our own in-memory format, which would have been smaller but would have isolated us from a thriving ecosystem.

We chose the Model Context Protocol because it's the only standard for AI tool integration that has any momentum, it's published by Anthropic, and it works with multiple clients including local LLM setups. We considered building a custom HTTP API and having clients integrate with us specifically, but that approach scales badly: every client needs custom integration, every model change needs to be re-validated, and we'd be a single point of failure. With MCP, we publish the server once and any compatible client benefits.

We chose Apache 2.0 over MIT for the license because the explicit patent grant matters for corporate adoption and protects contributors. The wordiness of Apache 2.0 is a non-issue in practice.

We chose to make the recorder opt-in via decorator rather than capture-everything-by-default because the alternative produces traces that are too large to be useful. The user knows where they're hunting; we let them scope the capture accordingly.

We chose to summarize values rather than capture them in full because full capture is impossible at any reasonable scale. The summary representation preserves enough information to answer typical debugging questions while keeping trace sizes manageable.

## How to extend it

The architecture supports extension along multiple axes. New languages get new recorders that emit the trace format; nothing else changes. New event types get added to the trace format with a version bump; old readers ignore unknown events. New MCP tools get added to the server; existing tools don't change. New analysis backends could replace DuckDB if a future maintainer wants to, since the indexer is a thin layer over the format.

The single hard constraint is the trace format itself. Once we have third-party recorders, breaking changes to the format become expensive. We version the format and add fields rather than reorganizing existing ones. The format spec is the contract that lets the project become a protocol rather than a tool.
